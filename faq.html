Product

What Fronesa is, and what it isn't.

What does Fronesa do?

Fronesa is a decision API. You send it a piece of text; it returns a decision (for example spam or ham), a confidence score between 0 and 1, and an escalation flag. When the flag is set, the model is explicitly saying "I don't know" — you're expected to route that case to a human reviewer, not act on it automatically.

The product's thesis is decisions that learn: your reviewers' corrections feed a retraining loop, so the model improves on your data over time. See the Method section for the full picture.

How is this different from a plain text classifier?

Three things a raw classifier doesn't give you:

  • An escalation contract. Every response carries an escalated boolean. Below the confidence threshold, we don't guess — we hand the decision to your humans. That contract is documented in the API reference, not buried in a blog post.
  • A learning loop. Reviewer corrections submitted through POST /review accumulate in a ledger; once 50 new labels exist, a retraining candidate is built and promoted only if it beats the current model on a held-out set. Details in our changelog as the loop ships.
  • An audit trail. Every response carries a model version and every request a request ID, so you can reconstruct exactly what the API said and why.
What languages are supported?

English. The production model is trained on English text; other languages are not supported yet. Multilingual support is on the roadmap but has no date.

What does "escalated" mean, exactly?

It means the model's confidence fell below its escalation threshold — the model is telling you it isn't sure. The contract is simple: do not auto-act on escalated decisions. Route them to human review (or a stronger model), and optionally send the reviewer's verdict back through POST /review so the loop learns from it.

Error items in batch responses are also marked escalated — same rule applies.

What kinds of decisions can the API make?

Today: spam vs. ham on English text. The decision vocabulary is model-specific and will grow as we ship new models — each response tells you which model version produced it, so you'll always know what you're getting.

Technical

Integration details, verified against our API spec.

How do I authenticate?

With a Bearer API key in the Authorization header:

Authorization: Bearer YOUR_KEY

Missing or invalid keys get a 401 with a machine-readable error code and a request ID. Keys are never accepted in URLs.

What are the rate limits?

100 requests per minute per key on /decide and /decide/batch. Exceeding it returns 429 with a Retry-After header telling you how long to wait.

Important: a batch of N texts counts as N requests — each text is one unit of model compute, so a 100-text batch consumes the full minute's budget. POST /review is more generous at 600 requests per minute.

How fast is it?

About ~2 ms per decision on a warm container (server-measured; a 100-text batch runs in roughly 4–5 ms end to end). These are lab measurements on our infrastructure, not a guaranteed SLA — see below.

But the first request after idle is slow: the free tier sleeps after ~15 idle minutes, and waking it up can take up to ~90 seconds. So "how fast" has two answers — ~2 ms warm, up to ~90 s on a cold start. The latency_ms field in each response measures only the model's decision time, not the container boot, so it reads ~2 ms even when your request waited 90 s for the container to wake.

What are cold starts — why is the first request slow?

The API runs on free-tier hosting, which puts the container to sleep after about 15 idle minutes. The first request after that has to boot the whole stack — up to ~90 seconds. Subsequent requests answer in ~0.1 s until the next idle period. Nothing is broken when this happens; it's the documented behavior of the free tier. If your use case can't tolerate a slow first request, warm the service with an unauthenticated GET /health call before you need it.

Do you offer an SLA?

No. We don't promise uptime or latency targets today — the API runs on free-tier hosting, and it would be dishonest to sell guarantees on infrastructure we don't control. If SLAs matter to you, tell us; it's one of the things paid hosting would unlock.

What happens when the API escalates — do I get notified?

The escalation flag comes back in the API response itself — your code checks escalated and routes accordingly. Push notifications (webhooks) for escalated items are on the roadmap but not shipped yet.

Is there an SDK?

Yes — a Python SDK (fronesa) with sync and async clients, retries with backoff, and a typed exception hierarchy. It's currently in pre-release while we finish publishing it to PyPI; the SDK docs page tracks its status honestly. REST works with any language today — see Getting started.

Pricing

What things cost, and what counts.

How am I billed?

Per decision, in monthly tiers. Current plan (see the pricing page):

  • Sandbox — free, 10,000 decisions/month.
  • Growth — $49/month + $0.50 per 1,000 decisions (1M included).
  • Scale — $499/month + $0.40 per 1,000 decisions (5M included).
  • Enterprise — custom.

Honest note: paid plans aren't live yet — early access is free while we finish billing. Prices are in USD and marked as planned rates, finalized after our first design-partner conversations.

What counts as a decision?

One /decide call = one decision. One /decide/batch call with N texts = N decisions. Rejected calls (401, 429) are never billed. Escalated decisions count the same as confident ones — the model still did the work.

What are the free tier limits?

Sandbox gives you 10,000 decisions per month, one model version, and community support. No credit card, no expiry — but rate limits still apply (100 requests/minute per key).

Can I cancel?

Growth and Scale are month-to-month — cancel anytime, no lock-in. Enterprise plans are annual by negotiation.

Security & privacy

What we do with your data, and what we don't.

Do you store the texts I send?

No. API request logs record metadata only — timestamp, endpoint, status, latency, and counts. They never contain your message contents or your raw API key (keys are stored as one-way hashes). Raw request logs are kept 30 days; aggregated daily summaries are kept 12 months.

Pilot customer data is handled separately: kept only for the pilot duration plus a short wind-down window (typically 30 days), isolated per pilot, and deleted on request at any time. Full details on the Data handling page.

Do you train your models on my data?

Never without your written consent. The learning loop only trains on review decisions you explicitly submit through POST /review — that endpoint is the opt-in path. Your ordinary /decide traffic is never used for training.

Where is data processed?

On our hosted API infrastructure (currently cloud hosting; the exact region isn't something we've published yet — ask us if it matters for your compliance review). We don't offer regional data residency today — if that's a requirement for you, say so; it's on the Enterprise roadmap.

What certifications do you hold?

None yet. No SOC 2, no ISO 27001, no independent penetration test, no bug bounty. Our security page documents what we actually do (key handling, fail-closed auth, error hygiene) instead of implying assurances we haven't earned.

How do I report a vulnerability?

Email surety.ai@proton.me with the details. We'll acknowledge within two business days and keep you posted on the fix. Please don't publish the details before we've had a chance to patch.
