Migration guide

From Perspective to Fronesa.

Google's Perspective API will no longer be in service after 2026, with no direct migration support and no new signups. (One team's August 2026 setup attempt hit PERMISSION_DENIED on new-project API enablement — see Sources below.) This guide helps former Perspective users evaluate Fronesa as a replacement — including where the mapping breaks, because it does break in places.

DRAFT — LAST UPDATED 2026-10-06
Honest disclaimer up front: Perspective was a toxicity-scoring API. Fronesa is a decision API with a confidence-scored escalation path. They are not the same shape. This guide shows you exactly where the differences are so you can migrate with your eyes open.

1. What Perspective gave you

The shape you're migrating from.

Perspective scored comments on toxicity attributes and returned per-attribute probability scores. You set your own thresholds and made your own decisions.

Endpoint: POST https://commentanalysis.googleapis.com/v1alpha1/comments:analyze?key=YOUR_API_KEY

Request shape:

{
  "comment": { "text": "You are terrible" },
  "requestedAttributes": {
    "TOXICITY": {},
    "INSULT": {},
    "THREAT": {}
  },
  "languages": ["en"]
}

Response shape:

{
  "attributeScores": {
    "TOXICITY": {
      "summaryScore": { "value": 0.87, "type": "PROBABILITY" }
    },
    "INSULT": {
      "summaryScore": { "value": 0.82, "type": "PROBABILITY" }
    },
    "THREAT": {
      "summaryScore": { "value": 0.12, "type": "PROBABILITY" }
    }
  },
  "languages": ["en"]
}

The 8 production attributes (per public documentation): TOXICITY (rude/disrespectful), SEVERE_TOXICITY (very hateful), IDENTITY_ATTACK (negative toward a group), INSULT, PROFANITY, THREAT, SEXUALLY_EXPLICIT, FLIRTATION.

Rate limits (public documentation): free tier ~1 request/second; paid tier up to ~10 requests/second.

What "the score" meant: a value between 0 and 1 representing the probability that a reader would perceive the comment as having the requested attribute. You decided the threshold (0.7 was a common choice) and the action.

2. What Fronesa gives you instead

The shape you're migrating to.

Fronesa makes a decision — not a score dump. It returns one verdict plus a confidence and an explicit escalation flag for cases it isn't sure about.

Endpoint: POST https://fronsea-api.onrender.com/decide

Request shape:

POST /decide
Authorization: Bearer <your-key>
Content-Type: application/json

{"text": "You are terrible"}

Response shape:

{
  "decision": "spam",
  "confidence": 0.93,
  "escalated": false,
  "version": "spam-v1",
  "latency_ms": 12
}

Rate limit: 100 requests/minute per API key (HTTP 429 + Retry-After when exceeded).

3. Side-by-side migration

Python and JavaScript, before and after.

Python: threshold on TOXICITY

Before (Perspective):

import requests

url = "https://commentanalysis.googleapis.com/v1alpha1/comments:analyze"
payload = {
    "comment": {"text": text},
    "requestedAttributes": {"TOXICITY": {}},
    "languages": ["en"],
}
r = requests.post(url, params={"key": API_KEY}, json=payload).json()
score = r["attributeScores"]["TOXICITY"]["summaryScore"]["value"]
action = "hide" if score >= 0.7 else "allow"

After (Fronesa):

import requests

r = requests.post(
    "https://fronsea-api.onrender.com/decide",
    headers={"Authorization": f"Bearer {FRONESA_KEY}"},
    json={"text": text},
).json()

if r["escalated"]:
    action = "send_to_human_review"
elif r["decision"] == "spam":
    action = "hide"
else:
    action = "allow"

What changed in the logic: you no longer pick a threshold. Fronesa's model proposes a decision and a confidence; the escalated flag marks items where the model is uncertain, and those go to your human reviewers. Your old threshold logic becomes a routing policy: your policy acts on high-confidence proposals, your reviewers own the escalated ones.

JavaScript (comment forms / live chat)

Before (Perspective): parse attributeScores.TOXICITY.summaryScore.value, compare to your threshold.

After (Fronesa): read decision + escalated. The two-branch pattern:

const r = await fetch("https://fronsea-api.onrender.com/decide", {
  method: "POST",
  headers: {
    "Authorization": `Bearer ${FRONESA_KEY}`,
    "Content-Type": "application/json"
  },
  body: JSON.stringify({ text })
}).then(x => x.json());

if (r.escalated) {
  // show "under review" state, queue for moderator
} else if (r.decision === "spam") {
  // hide / reject
} else {
  // publish
}

5. The three big mapping gaps

Read this before migrating. Honestly.

Gap 1: Per-attribute scores → one decision

Perspective returned a separate probability for each of 8 attributes. If your product logic keys on specific attributes — e.g. auto-block on THREAT ≥ 0.8 but only warn on PROFANITY ≥ 0.6 — there is no equivalent in Fronesa today. We return one decision per text. You will need to collapse your per-attribute rules into a single policy: which attribute outcomes map to "block", which to "review", which to "allow". For some teams this is a simplification; for others it's a real loss of granularity.

Gap 2: Toxicity categories ≠ our current model

Our production model is a spam/ham text classifier with measured lab performance (accuracy 0.9875, zero false positives on the held-out split). It is not a toxicity classifier. IDENTITY_ATTACK, SEVERE_TOXICITY, THREAT, SEXUALLY_EXPLICIT and friends are not categories we score. If your core use case is hate-speech or threat detection rather than spam/abuse triage, Fronesa is not a drop-in replacement today — and we won't pretend it is.

Gap 3: Languages and scale

Perspective supported many languages with automatic detection. Fronesa's current model is English-focused. Perspective also served at Google scale with paid tiers up to 10 req/s; our rate limit is 100 requests/minute per key on free infrastructure. If you need many languages or thousands of requests per second, we are not there yet.

6. Migration checklist

Eight steps, in order.

  • Inventory your Perspective usage. List every requestedAttributes value you use and the threshold + action for each. (You can't map what you haven't listed.)
  • Collapse per-attribute rules to one policy. Decide which attribute outcomes = block, which = human review, which = allow. The gray-area ones map to Fronesa's escalated path.
  • Audit your language mix. If non-English traffic is material, Fronesa is not ready for you yet — check back or talk to us.
  • Rewire the decision branch. Replace score >= threshold with the three-way escalated / decision routing shown above.
  • Wire up the review queue. The escalated flag only helps if someone reads the queue. Assign reviewers before you switch traffic.
  • Run shadow mode for 2 weeks. Send the same traffic to Fronesa and log decisions alongside your existing logic. Compare disagreement rates before cutting over.
  • Update your own users' copy. If your UI said "checked by Perspective" or showed toxicity scores, update it. Don't present Fronesa decisions as Perspective scores.
  • Check your rate-limit headroom. 100 req/min per key; request more keys or talk to us if you're above that.

7. Honest limitations

What we don't claim.

  • We don't cover as many languages as Perspective did — English-focused today.
  • We don't return per-attribute toxicity scores — one decision, one confidence, one escalation flag.
  • We don't have a decade of production history — our numbers are lab-measured, clearly labeled as such, on a held-out spam dataset.
  • We don't offer an SLA on free hosting — and we say so plainly in our developer terms.
  • We are not SOC 2 / ISO 27001 certified and have not had an independent pen test — documented on our security page.

What we do offer: a decision API designed to learn from your reviewers' corrections over time, an escalation path that keeps humans in the loop for the hard cases, and honest numbers about what the model can and can't do.

8. Who this is for

Is this guide for you?

This guide is aimed at teams orphaned by the Perspective shutdown: publishers, community platforms, comment-section operators, and researchers who used the API's free tier for toxicity scoring. If your workload was "score this comment, apply my threshold," sections 3–4 get you migrated. If your workload depended on specific attributes or non-English languages, section 5 tells you honestly whether to wait.

Also migrating from Azure?

If you're coming from Azure rather than Perspective, watch out: Azure's Content Safety custom categories (standard) API is being retired, and Microsoft's recommended replacement — Foundry's "custom text classification" (Azure Language) — is itself scheduled for retirement on March 31, 2029. The Azure Language Studio portal retires even sooner, on March 20, 2027. So the official path is a forced migration now followed by a second forced migration within ~2.5 years. We cover both Azure retirements — and what actually replaces the dead-simple "define your own categories" workflow — in an upcoming deep-dive (week of December 15). If you want a custom-policy classifier without a studio project to babysit and no 2029 re-migration, talk to us.
