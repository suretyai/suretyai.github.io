Honest eval · Part 24

Our test suite was green because of import order.

We run 230 tests and they all pass. Except: they pass because pytest collects files alphabetically. Change the order and four tests fail with 401s.

Fronesa engineering October 6, 2026 5 min read

The news

We run 230 tests and they all pass. Green badge, clean conscience, move on.

Except: our test suite was green because of alphabetical order.

Here is what QA found this week. Run the suite the normal way and you get 230/230 PASS. Run it with two files listed first — test_webhook_dlq.py or test_webhook_payload_conformance.py before test_review.py — and four review tests fail with 401s. Not flaky. Not environmental. Deterministic: reproduce it every time, root-cause it, fix it.

The root cause

The root cause is a one-line sin repeated in two files. Both modules import decivia.api without setting DECIVIA_ADMIN_KEYS first. The API reads its admin keys from the environment once, at import time — whichever module imports first freezes ADMIN_KEYS for the whole session. If the first import comes from a module that never set the admin key, the key list is empty, and every test authenticating as t-admin gets a 401 instead of the expected result.

The suite passed 230/230 for one reason: pytest collects files alphabetically, and test_review.py sorts before test_webhook_*.py. The correct module imported first, every time, by luck of the alphabet. Had anyone named the file test_admin_webhooks.py, we'd have been red for weeks — and would never have known the badge was a coincidence.

A test suite that passes by accident is a machine for manufacturing false confidence.

Why "test-only" is not "harmless"

This is a test-only bug. The product code is unaffected: production loads its keys once, from its own config, and never from a sibling module's import order. But "test-only" is not "harmless." A test suite that passes by accident is a machine for manufacturing false confidence. It told us "230/230" and what it meant was "230/230 in exactly this order." We were reporting the first thing while believing the second.

The fix is two lines: set the admin-key default at the top of both modules before the import, matching the convention the other modules already use.

The lesson

A green suite is a claim, and every claim needs its own audit. Our honest-eval series exists because we audit our models this way. This week we learned to audit our audits.

We could have fixed this quietly and kept the badge. We chose to publish the embarrassment instead, because the series has one rule: we write about the misses we catch, not just the ones we prevent. The four tests are fixed. The import order is not luck anymore. And the next time the badge is green, we'll know what the badge actually means.

Chain of custody

Verified, reproduced, and bisected by Nadia (QA) 2026-10-06 ~09:15 +03. Failing tests: test_review_customer_pending_isolation, test_review_rejects_oversized_customer_id, test_review_accepts_max_length_metadata, test_review_accepts_valid_reviewed_at — all authenticate with key="t-admin", all fail 401 == 400 when test_webhook_dlq.py or test_webhook_payload_conformance.py imports first. Root cause: neither module sets DECIVIA_ADMIN_KEYS before importing decivia.api; ADMIN_KEYS = load_admin_keys() reads the environment once at import. Full suite passes (230/230) only because pytest's alphabetical collection imports test_review.py before test_webhook*.py.

Recommended fix from the QA report: add the admin setdefault (DECIVIA_ADMIN_KEYS=t-admin) to the payload and dlq modules' import-time setdefaults, matching the union-comment convention. Product code unaffected.

Pre-publish blockers

  1. Fix must land first. Do not publish until the two-line fix is merged and the reordered suite re-run is recorded (230/230 in adversarial import order, not just alphabetical).
  2. Verify the four test names against the final diff — publish the exact names from the merged code, not this draft.
  3. No "we test better than everyone" framing. The piece confesses a testing miss; it must not pivot into a superiority claim about our QA process.
  4. Braa review. Standard for all honest-eval parts before publication.
  5. Date-stamp the claim. "This week" must become a concrete date at publish time; stale embarrassments published late read as PR.
