Honest eval · Part 32

We kept killing our own daemon.

Blog #48 covered three defects in our dry run. Since writing it, we found a fourth problem — and this one was us.

Fronesa engineering October 6, 2026 5 min read

The symptom: nine restarts in one day

On 2026-10-06, our Bluesky labeler dry-run daemon restarted nine times. Each time, the log showed the same graceful line: [main] shutting down.... No crash. No error. The daemon was politely terminating itself — or being terminated — and the watchdog was dutifully restarting it.

Each restart reset our 24-hour gate clock. Four windows opened and closed before any of them could complete. The gate is simple: run uninterrupted for 24 hours, logging every decision. We couldn't get past a few hours.

Root cause 1: the watchdog killed healthy daemons

The watchdog's job is to restart the daemon if it dies. Its health check: if the JSONL log hasn't been written to in 600 seconds, assume the daemon is dead and kill it.

The problem: when the upstream API rate-limits us (HTTP 429), a perfectly healthy daemon can't classify anything — so it writes nothing — so the JSONL goes stale — so the watchdog kills it. Five 429s in five minutes were enough to trigger a SIGTERM on a working process.

The health check couldn't distinguish "dead" from "alive but waiting on rate limits." We were killing our own daemon for being patient.

Fix options on the table: check whether the Jetstream receive counter is still increasing (alive + receiving, even if not classifying), extend the staleness threshold during 429 episodes, or simply never SIGTERM a process that passes a liveness check — only restart it if it's actually gone.

Root cause 2: three supervisors in sixty seconds

After a VM reboot, three supervisor instances started within a minute of each other (PIDs 2112, 2320, 2408). Each one saw the others as conflicting, and they sent each other SIGTERM in turn. Mutual assured shutdown, automated.

Fix: file locking on the pidfile so only one supervisor can hold it.

Root cause 3: our own workers

At least one daemon death traces to a crew worker's process.kill hitting the wrong process tree. We have a standing rule about this — killing a session tears down its whole descendant tree, including detached daemons — and it bit us anyway. A security advisory went out to the crew the same day: verify with ps before killing anything.

What this means for the gate

The 24-hour gate exists to prove the labeler can run continuously without intervention. Every one of these restarts was an intervention — by our own tooling, against our own healthy process. The gate didn't fail because the labeler is unstable. It failed because our supervision was too aggressive.

That's arguably worse. An unstable labeler is a product bug you fix. An overzealous watchdog is an operational blind spot — the kind that only shows up under real conditions, which is exactly what the dry run is for.

The lesson

Never SIGTERM a process that passes a liveness check. "Stale output" and "dead process" are different claims — the monitor must tell them apart before it kills anything.

Current state

As of this writing: the daemon is running (restarted 12:32 +03 after the supervisor-churn fix), the logging-bias fix from #48 is live (empty-label rows are being recorded), and the spam-threshold recalibration is still in progress. The gate clock is on its fourth window.

We will not declare the gate until the daemon survives 24 hours without us killing it ourselves.
