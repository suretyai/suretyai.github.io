Security, stated plainly.

How we protect your API keys and your data, what we don’t do, and how to tell us if something looks wrong. Written for humans, not auditors — which also means we say what we haven’t done yet.

LAST UPDATED — OCTOBER 2026

1. How API keys work

Every API call carries your key in the Authorization: Bearer header. Requests without a valid key are rejected — the service fails closed: no key, no answer, no partial data.

  • Rate limited per key: 100 requests per minute. Over the limit you get HTTP 429 with a Retry-After header — back off and retry.
  • Request size capped: 64 KB maximum body on /decide; oversized requests are rejected before they’re read.
  • Keys are isolated: each pilot gets its own key, and activity is tracked per key so one customer’s traffic never affects another’s.

2. If your key leaks

Treat an API key like a password: keep it in server-side environment variables or a secrets manager, never in client-side code, public repos, or chat messages.

If a key is exposed, write to us immediately at surety.ai@proton.me. We will revoke the old key and issue a new one — we add the replacement first and verify it before removing the old one, so there’s no downtime. You are responsible for traffic sent with your key until it’s revoked, so tell us fast.

3. Your data, in brief

The full detail lives on the data handling page; the short version for this page:

  • All API traffic is encrypted in transit over HTTPS (TLS).
  • Stored pilot data sits on access-controlled infrastructure, reachable only by the small team operating the pilot.
  • Each pilot’s data is kept separate — separate keys, separate storage, separate model versions.
  • No training on your data without your explicit written consent. Your private model version retrains on your resolved escalations only; nothing of yours flows into anyone else’s model.
  • Deletion on request, any time: surety.ai@proton.me.

4. What we don’t do

  • We don’t sell your data. Not to advertisers, not to data brokers, not to anyone.
  • No third-party analytics on your texts. Your API traffic is never routed through marketing trackers or analytics dashboards.
  • We don’t read your review queue. Escalated decisions go to your own reviewers; we don’t see that content unless you explicitly invite us to a joint debugging session.

5. Report a vulnerability

Found something? We want to hear it before anyone else exploits it. Email surety.ai@proton.me with “security” in the subject line and include:

  • What you found and where (endpoint, page, or behavior).
  • Steps to reproduce, if you can share them safely.
  • How we can reach you for follow-up questions.

We aim to acknowledge every report within 2 business days and keep you updated as we investigate and fix. Please don’t publish details before we’ve had a chance to fix the issue — give us a reasonable window and we’ll be straight with you about progress.

Good faith, no retaliation: we won’t pursue legal action against researchers who report vulnerabilities in good faith, stay within the scope of the issue, and don’t access, modify, or exfiltrate other customers’ data. Please don’t test against other pilots’ keys or data — there’s nothing of theirs we want you touching, and nothing of theirs for you to find.

We don’t run a bug bounty program at this stage — we’ll say so plainly rather than imply one. If that changes, this page changes first.

6. Infrastructure, honestly

The pilot API runs on Render’s managed platform (free tier), which handles the underlying OS patching, network isolation, and TLS termination. On top of that we run our own application with the key auth, rate limiting, and request-size caps described above.

Honest limitations of the free tier, since they matter to you:

  • The service can cold-start after idle periods — the first request may take longer.
  • There is no uptime guarantee during the pilot (see pilot terms).
  • Resource limits (memory, CPU) are those of the free tier — which is one reason our pilot limits are set where they are.

Our keys and configuration are stored as server-side environment variables, never baked into code or images. Application logs carry request IDs for debugging; they don’t carry your API keys or your texts.

7. What we don’t claim

Plainly, and consistent with our other pages:

  • No security certifications — no SOC 2, no ISO 27001. If your procurement requires them, tell us early and we’ll say so directly.
  • No independent penetration test has been conducted yet. It’s on the list as the pilot matures; until then we won’t imply otherwise.
  • Everything on this page is our operating practice, stated honestly — not an audited standard. When a practice changes, this page changes with it.

8. Contact

Security questions or reports: surety.ai@proton.me — a human reads it, and security mail gets priority.
